1. EXECUTIVE SUMMARY & PROBLEM STATEMENT
================================================================================
1.1 Background:
On modern higher education campuses, tens of thousands of daily student and staff 
movements occur across lecture complexes, research laboratories, libraries, 
cafeterias, sports facilities, and transit gates. Belongings such as laptops, 
campus ID cards, room keys, textbooks, smartwatches, and headphones are frequently 
misplaced.

1.2 Existing System Deficiencies:
1. Fragmented Communication: Reports are scattered across unofficial WhatsApp 
   groups, student forums, social media, and physical security desks.
2. Privacy Hazard & Fraud: When students post photos with unique markings, serial 
   numbers, or lockscreen wallpapers, fraudulent claimants can easily impersonate 
   ownership and claim valuable electronics.
3. Slow Heuristic Correlation: There is no systematic way to correlate a lost item 
   report with an item deposited at a campus security custody desk.
4. Zero Handover Traceability: Traditional handovers lack tamper-proof digital passes 
   and immutable audit trails.

1.3 The Solution:
The Smart Lost & Found Intelligence System solves these problems with a secure, 
closed-loop recovery pipeline combining managed cloud database infrastructure, 
NLP-based heuristic similarity scoring, confidential evidence verification, 
and short-lived cryptographic QR handover tokens.

2. PROPOSED SYSTEM & KEY OBJECTIVES
================================================================================
- Objective 1: Centralize lost and found reporting across curated campus zones 
  (Central Library, Auditorium, Engineering Block, Science Block, Activity Center, 
  Cafeteria, Sports Ground, North Gate Security).
- Objective 2: Automated Heuristic Matching that evaluates category, textual 
  description overlap, elapsed time, campus proximity, and physical attributes.
- Objective 3: Strict Zero Public Clue Exposure: public descriptions contain only 
  generic visual details; private identifying clues (wallpapers, serial numbers, 
  pouch contents) are strictly restricted to the claimant and authorized moderators.
- Objective 4: Cryptographically Verified QR Handover: single-use, 24-hour expiring 
  digital passes that prevent token replay and record physical handover events.
- Objective 5: Demonstrate Authentic Cloud Computing: Database-as-a-Service (DBaaS), 
  Authentication-as-a-Service, Cloud Object Storage with presigned URLs, and 
  database-level Row-Level Security.

3. SYSTEM ARCHITECTURE & CLOUD SERVICE MODEL
================================================================================
The application utilizes a decoupled, three-tier cloud-native architecture:

1. PRESENTATION TIER (Browser / Client):
   - React 18 & Vite: High-performance single page application.
   - Tailwind CSS: Modern light-first glassmorphism styling and responsive layout.
   - Three.js / React Three Fiber / Drei: Interactive 3D hero scene with floating 
     belongings and low-power mobile fallbacks.
   - Framer Motion: Route and modal animations.
   - Recharts: Admin telemetry and category distribution visualizations.
   - QRCode SVG: Dynamic generation of one-time digital recovery passes.

2. APPLICATION SERVER TIER (Node.js & Express REST API):
   - Stateless REST API running on port 5000.
   - Helmet: Secures HTTP response headers.
   - Express Rate Limit: Protects against denial-of-service and brute force.
   - JWT Auth Middleware: Cryptographically verifies Bearer tokens and loads roles.
   - Role-Based Access Control (RBAC): Enforces permissions for Student, Staff, 
     Moderator, and Administrator.
   - Heuristic Engine: Executes tokenized text similarity and scoring.
   - Multer Middleware: Handles memory-streamed image uploads capped at 5MB.

3. CLOUD DATA TIER (Supabase Cloud):
   - PostgreSQL DBaaS: High-performance relational database with indexing.
   - Supabase Auth: Managed GoTrue identity provider issuing signed JWTs.
   - Supabase Storage: Private bucket 'item-images' with 1-hour presigned URLs.
   - Row-Level Security (RLS): Database-level isolation on every exposed table.
   - Local Memory Store: Built-in offline fallback store for immediate local testing.

4. DATABASE DESIGN & RELATIONAL SCHEMA (11 TABLES)
================================================================================
The database architecture comprises 11 relational tables linked via UUID primary 
keys and foreign keys:

1. profiles:
   - id: UUID (PK, references auth.users.id)
   - display_name: TEXT NOT NULL
   - campus_email: TEXT UNIQUE NOT NULL
   - role: TEXT CHECK (role IN ('student', 'staff', 'moderator', 'admin'))
   - department: TEXT
   - is_active: BOOLEAN DEFAULT TRUE
   - created_at / updated_at: TIMESTAMPTZ

2. categories:
   - id: UUID (PK)
   - name: TEXT UNIQUE (Electronics, Wallets, Keys, Bags, Books, Clothing, etc.)
   - description: TEXT
   - icon: TEXT
   - is_active: BOOLEAN DEFAULT TRUE

3. campus_locations:
   - id: UUID (PK)
   - name: TEXT UNIQUE (Central Library, Main Auditorium, etc.)
   - zone_code: TEXT (LIB-01, AUD-01, etc.)
   - latitude / longitude: NUMERIC(10, 7)
   - is_active: BOOLEAN DEFAULT TRUE

4. reports:
   - id: UUID (PK)
   - owner_id: UUID (FK -> profiles.id)
   - report_type: TEXT CHECK ('lost', 'found')
   - title: TEXT NOT NULL
   - description_public: TEXT NOT NULL
   - category_id: UUID (FK -> categories.id)
   - location_id: UUID (FK -> campus_locations.id)
   - event_at: TIMESTAMPTZ NOT NULL
   - colour: TEXT
   - brand: TEXT
   - private_notes: TEXT (Strictly confidential; never returned in public APIs)
   - status: TEXT CHECK ('open', 'matched', 'claimed', 'recovered', 'closed', 'rejected')
   - created_at / updated_at / closed_at: TIMESTAMPTZ

5. report_images:
   - id: UUID (PK)
   - report_id: UUID (FK -> reports.id)
   - storage_path: TEXT NOT NULL
   - mime_type: TEXT NOT NULL
   - file_size_bytes: BIGINT NOT NULL
   - is_primary: BOOLEAN DEFAULT FALSE

6. matches:
   - id: UUID (PK)
   - lost_report_id: UUID (FK -> reports.id)
   - found_report_id: UUID (FK -> reports.id)
   - category_score / text_score / date_score / location_score / attribute_score: NUMERIC
   - final_score: NUMERIC (0.00 to 100.00)
   - explanation: JSONB (Human-readable match reasons)
   - status: TEXT CHECK ('suggested', 'reviewed', 'dismissed', 'claimed')
   - CONSTRAINT: UNIQUE (lost_report_id, found_report_id)

7. claims:
   - id: UUID (PK)
   - found_report_id: UUID (FK -> reports.id)
   - match_id: UUID (FK -> matches.id, NULLABLE)
   - claimant_id: UUID (FK -> profiles.id)
   - private_answers: JSONB NOT NULL (Lockscreen wallpapers, unique scratch clues)
   - status: TEXT CHECK ('pending', 'info_requested', 'approved', 'rejected', 'cancelled')
   - moderator_id: UUID (FK -> profiles.id, NULLABLE)
   - decision_reason: TEXT

8. handover_tokens:
   - id: UUID (PK)
   - claim_id: UUID (FK -> claims.id)
   - token_hash: TEXT UNIQUE NOT NULL (HMAC-SHA-256 hash)
   - expires_at: TIMESTAMPTZ NOT NULL
   - redeemed_at: TIMESTAMPTZ (NULLABLE, recorded upon one-time redemption)
   - created_by: UUID (FK -> profiles.id)

9. notifications:
   - id: UUID (PK)
   - user_id: UUID (FK -> profiles.id)
   - type / title / body_public: TEXT
   - related_report_id / related_claim_id: UUID (NULLABLE)
   - is_read: BOOLEAN DEFAULT FALSE

10. watchlists:
    - id: UUID (PK)
    - user_id: UUID (FK -> profiles.id)
    - criteria: JSONB NOT NULL
    - is_active: BOOLEAN DEFAULT TRUE

11. audit_logs:
    - id: UUID (PK)
    - actor_id: UUID (FK -> profiles.id, NULLABLE)
    - action: TEXT NOT NULL
    - entity_type: TEXT NOT NULL
    - entity_id: UUID (NULLABLE)
    - metadata_safe: JSONB
    - created_at: TIMESTAMPTZ

5. SECURITY, ROW-LEVEL SECURITY & PRIVACY GUARDRAILS
================================================================================
1. Zero Public Clue Exposure:
   The public catalog displays only generic visual attributes. Passwords, serial 
   numbers, and inner contents are isolated in 'private_notes' and 'private_answers', 
   accessible solely by the owner and authorized staff.

2. Row-Level Security (RLS):
   PostgreSQL RLS policies are enabled on all tables:
   - Students can SELECT and UPDATE only their own claims and notifications.
   - Moderators/Admins have access to the moderation queue via verified policy.
   - Direct database access queries enforce user ID boundaries even if an API route 
     is bypassed.

3. Private Cloud Object Storage:
   Item photos reside in private Supabase Storage buckets. Clients receive temporary 
   presigned cryptographic URLs with a 1-hour expiration time.

4. Cryptographic Single-Use QR Pass:
   Upon claim approval, the system generates an opaque 48-character random token. 
   The database stores an HMAC-SHA-256 hash with salt. During physical custody 
   handover, the token is verified and marked 'redeemed_at = NOW()'. Repeated scans 
   are rejected immediately to prevent replay attacks.

6. INTELLIGENT HEURISTIC MATCHING ENGINE & ALGORITHM
================================================================================
The matching engine implements the primary formula specified in spec.md:

    Score = 0.30*Category + 0.25*Text + 0.20*Date + 0.15*Location + 0.10*Attributes

Component Breakdown:
- Category (30%): Exact category match = 1.0; mismatch = 0.0.
- Text (25%): Tokenized Jaccard lexical overlap and keyword matching between 
  title and description:
    Tokens = Set(Words > 2 chars, lowercase, alphanumeric)
    Jaccard Similarity = |Tokens1 ∩ Tokens2| / |Tokens1 ∪ Tokens2|
- Date (20%): Temporal proximity with sliding 14-day exponential decay:
    Score = Max(0, 1 - ElapsedDays / 14) (1.0 for same-day, 0.5 for 7 days)
- Location (15%): Exact campus zone match = 1.0; general campus zone = 0.2.
- Attributes (10%): Colour match (0.5) + Brand manufacturer match (0.5).

Score Bands:
- 80% to 100%: Strong Potential Match (Emerald Indicator)
- 60% to 79%:  Possible Match (Amber Indicator)
- Below 60%:   Low Similarity (Not prominently recommended)

Ethical Safeguard:
The UI strictly identifies scores as heuristic similarity percentages, never 
automated ownership proof. Human moderator verification of private clues is always 
mandatory.

10. VIVA DEFENSE & EXAMINATION QUESTIONS WITH ANSWERS
================================================================================
Q1: Why does this system qualify as a Cloud Computing project?
A1: It consumes authentic managed cloud services: Database-as-a-Service (DBaaS via 
    Supabase PostgreSQL), Authentication-as-a-Service (JWT GoTrue), and Object 
    Storage-as-a-Service (private bucket with presigned cryptographic URLs), coupled 
    with database-level Row-Level Security (RLS) and centralized audit logging.

Q2: Why doesn't the AI auto-approve ownership when the score is high?
A2: A similarity score is a statistical heuristic, not legal proof. Many students own 
    identical items (e.g. black laptop sleeves). Automated approval would enable 
    theft. The AI accelerates discovery; human moderators verify private clues.

Q3: How does the system prevent QR code screenshot sharing and replay attacks?
A3: When an approved claim generates a handover pass, the raw token is hashed using 
    HMAC-SHA-256 with a secret salt. During handover, the custody officer's scan 
    records 'redeemed_at = NOW()'. If the token is scanned again, the server rejects 
    it immediately as already redeemed. Tokens also have a 24-hour expiration window.

Q4: What happens if the cloud AI or storage service goes down?
A4: The architecture follows graceful degradation. If cloud storage or image 
    similarity fails, the system continues to process reports and execute textual/metadata 
    matching without blocking report creation.
